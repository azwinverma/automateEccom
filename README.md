# Nivaro — Autonomous Commerce OS

**Your store, on autopilot.**
**From product photo to delivered order — automatically.** Your store runs itself. You handle exceptions.

Nivaro is an autonomous operating system for online and social-commerce sellers (initial market: Nepal). It runs the
commerce loop (catalog → content → conversations → orders → delivery → returns) and learns from outcomes to make
the merchant more profitable. Positioning: `specs/25_COMPETITIVE_POSITIONING_AND_USP.md`; roadmap: `specs/22`.
Product and engineering specs are in [`specs/`](specs/). Start with `specs/00_CLAUDE_START_HERE.md`.

Brand system: [`specs/26_NIVARO_BRAND_SYSTEM.md`](specs/26_NIVARO_BRAND_SYSTEM.md) · assets: [`assets/brand/`](assets/brand/).
Repository, package and service identifiers keep the legacy `commerce-os` / `commerce_os` names on purpose
(they are wired into imports, tokens, bundle IDs and data); see ADR-028 in `docs/DECISIONS.md`.

**Status:** Phases 0–1 engineering complete, exits blocked on external items. See [`docs/IMPLEMENTATION_STATUS.md`](docs/IMPLEMENTATION_STATUS.md),
[`docs/KNOWN_GAPS.md`](docs/KNOWN_GAPS.md) and [`docs/DECISIONS.md`](docs/DECISIONS.md).

## Run locally

**One command (recommended).** Needs PostgreSQL and Redis running (e.g. `brew services start postgresql@14 redis`), `uv` and `pnpm`:
```bash
cp apps/backend/.env.example apps/backend/.env   # first time only; set ports/DB (see below)
pnpm install                                     # first time only
scripts/dev.sh            # API + worker + web, hot reload      (or: scripts/dev.sh --prod)
```
It checks Postgres/Redis, refuses busy ports (and says which process holds them), migrates the database,
seeds the plans, then runs:

| What | URL |
|---|---|
| Website (public) | http://localhost:3010 |
| Sign up / sign in | http://localhost:3010/register · /login |
| Seller app | http://localhost:3010/home |
| API docs | http://localhost:8090/api/v1/docs |
| Dev emails (verification, invites) | `.data/mailbox/` |

Ports default to API 8090 and web 3010 (`API_PORT` / `WEB_PORT` to change). Keep these in step:
- `COS_PUBLIC_API_BASE_URL` in `apps/backend/.env` points at the API port.
- `COS_CORS_ORIGINS` lists the web origin first (it is also used for links in emails).
- `apps/web/.env.local` sets `BACKEND_URL`.

**Mobile app** (in a second terminal, with `scripts/dev.sh` running):
```bash
scripts/mobile.sh           # USB Android phone if connected (adb reverse), otherwise Chrome
scripts/mobile.sh android   # Android phone: enable USB debugging and accept the prompt on the phone
scripts/mobile.sh chrome    # Flutter web on http://localhost:5310
```

**Admin (platform staff):** register on the website, then `scripts/make-admin.sh you@example.com`. Then turn on
two-step sign-in (Settings → Security) and sign in again; admin endpoints require an MFA-verified session.

**AI:** without `COS_ANTHROPIC_API_KEY` (or OpenAI/Gemini) the sandbox provider produces placeholder drafts
marked `[sandbox]`, so the flows work end to end without a key.

**Everything in Docker** instead (Postgres, Redis, MinIO, migrations, API, worker, beat):
```bash
docker compose up --build          # API → http://localhost:8000
docker compose --profile web up    # + web → http://localhost:3000
```

## Quality gates
```bash
cd apps/backend && uv run ruff check app tests && uv run mypy app && uv run pytest   # needs Postgres + Redis
pnpm -r lint && pnpm -r typecheck && pnpm -r test && pnpm --filter @commerce-os/web build
cd apps/mobile && flutter analyze && flutter test
E2E_BASE_URL=http://localhost:3010 pnpm --filter @commerce-os/web e2e    # live stack
```
CI runs all of these plus migration checks, dependency audits, SAST, secret and container scanning (`.github/workflows/ci.yml`).

## Platform rules
- Business code never calls AI SDKs. It calls `app.domains.ai.gateway`.
- Business code never checks plan names. It asks `entitlements` for a feature or resource.
- Every state change writes an audit row in the same transaction.
- Durable side effects go through the outbox; events must be declared in `packages/contracts/event-catalog.json`.
- Merchant-owned tables use `TenantScoped`. Tenant filtering is automatic, and cross-tenant tests are required.
